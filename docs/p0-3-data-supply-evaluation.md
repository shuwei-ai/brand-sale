# P0-3「粉丝画像」数据供给评估：采集 + 检索组合方案

> 评估日期：2026-10-08
> 前置：[`docs/requirements-coverage-analysis.md`](./requirements-coverage-analysis.md)（缺口认定）、
> [`docs/datasource-candidate-evaluation.md`](./datasource-candidate-evaluation.md)（DTK / xhs 单项评估）
>
> 本文回答的问题：**把 DTK / xhs 的内容层数据，与已有的联网检索能力组合起来，
> 能否补上 P0-3「抖音明星粉丝画像 / 粉丝占比 / 年龄层分布」？**
> 结论比单看两个项目时**有实质性改变**——因为查到了官方通道，以及一个可用的地域代理。

---

## 0. 结论速览

**组合方案把 P0-3 从「完全缺失」提升到「地域可代理、年龄性别仍缺」——是部分满足，不能宣称满足。**

但更重要的是：**查到了三条之前不知道的合法取数通道**，其中一条**免费、官方、且正是需求要的那三项字段**。
P0-3 的真实瓶颈不在技术，在**商务与授权**。

| 供给路径 | 能供什么 | 成本 | 覆盖范围 | tier |
|---|---|---|---|---|
| ① 联网检索（**已有**） | 公开报告里的**品类级**人群画像 | 已有 | 品类大盘 | L3 |
| ② 巨量算数 / 抖音指数 | **关键词级**人群画像（年龄/性别/地域） | 网页版免费 | 内容/品类级 | L3 |
| ③ DTK / xhs（候选） | 达人账号 + 作品 + 评论（**含 `ip_label` 属地**） | 自托管 ≈ 0 边际 | 任意达人 | L3 |
| ④ **抖音开放平台 `fans_data`** | **账号级粉丝画像：年龄 / 性别 / 地域 / 兴趣 / 设备 / 活跃** | **官方免费** | **仅授权过的达人** | **L1** |
| ⑤ 星图品牌过审 / 蒲公英 + 第三方 API | 任意达人的粉丝画像 + 报价 + 商单转化 | 按次 / 按月 | **任意达人（含未合作）** | L2 / L4 |

**一句话**：① + ③ 组合是「便宜的近似」，④ 是「免费的精确但只覆盖已合作艺人」，
⑤ 是「要花钱的精确且覆盖候选池」。**① + ③ 永远替代不了 ④ / ⑤，但能显著改善地域维度。**

## 1. 从 ③ 里挖出的关键字段：评论 `ip_label`

单看 DTK 的归一化模型看不到它——`Comment` 模型只声明了
`comment_id / content_id / parent_id / text / created_at / digg_count / reply_count / author / is_author_liked / is_pinned`：
**没有地域字段**。

但有两件事改变了判断：

1. DTK 的模型文档明确写了设计原则：
   > Every model keeps the untouched platform payload in `raw` so new metrics can be
   > back-computed later without re-fetching.
   即 **原始 payload 保留在 `raw` 里**——新指标可以不改上游代码直接回算。
2. 抖音评论接口**确实返回 IP 属地**。这一点有多个独立来源交叉证实：

| 来源 | 字段 | 说明 |
|---|---|---|
| Apify `douyin-comments-scraper` | `ipLabel` | "Region shown by Douyin for the commenter (e.g. a province)" |
| Apify `toolzerhub/douyin-comments-scraper` | `ip_label` | "IP region shown next to the comment" |
| 次幂 cimidata API | `ip_label` | 与 `cid / text / digg_count / create_time / user.nickname` 并列返回 |
| 微界 bzapi | `"ip_label": 评论时ip` | 公开评论接口 |
| ClawHub `douyin-viral-breakdown` | `comments[].ip_label` | 示例值 `"广东"` |

**所以：评论 `ip_label` 是省级粒度的、可批量获取的、免费的字段。**
它使「用评论区反推粉丝地域分布」在**技术上可行**。

同一条链路还能顺带拿到：评论者 `sec_uid`（去重后可算「参与评论的去重用户数」，近似活跃粉丝规模）、
评论时间（活跃时段分析）、评论 `digg_count`（高赞评论的话题倾向）。

### 但第三方安全审计已经对这件事给出警告

ClawHub 对 `douyin-viral-breakdown` 这个技能的审计报告里，有一条 Medium 级（置信度 97%）发现，
针对的正是「聚合评论者 IP 属地」：

> Collecting commenter IP labels is not necessary for explaining why a video went viral and
> can expose coarse location metadata about third parties. Even if publicly surfaced by the
> platform, aggregating and processing this metadata creates avoidable privacy risk and
> exceeds the principle of data minimization.

这条审计意见必须原样带进方案。它说明：**技术可行 ≠ 应当做**。
而且它批评的恰恰是「把 ip_label 拉进一个不需要它的任务」——
这正是 brandsale 的治理哲学（数据最小化、用途约束）要避免的模式。

**结论：可以做，但要按下面四条约束做。**

| 约束 | 具体做法 |
|---|---|
| 粗粒度 | 只做**省级**聚合，不做市级、不做区县 |
| 只输出聚合量 | 报告里只写「地域占比」区间，**不落个人标识、不出个体** |
| 如实标注偏差 | 页面上标明「评论者地域分布（有偏代理，评论者 ≠ 粉丝总体）」 |
| 走一次隐私评审 | 新增此能力前过一遍 privacy 评审，确认不违反数据最小化 |

**偏差必须讲清楚**：评论者是**活跃子集**，比粉丝总体更年轻、更集中在一二线、
更愿意表达。抖音活跃用户的地域集中度本身就高于人口分布。
所以这个代理**只能做趋势性判断**（「粉丝以华东为主」），
**不能做精确断言**（「广东粉丝占 18.3%」）。

## 2. 之前漏掉的通道：抖音开放平台官方 `fans_data`

这是本次评估**最重要的发现**。

**接口**：`GET https://open.douyin.com/api/douyin/v1/user/fans_data/?open_id=...`
· Scope `fans.data.bind`

**返回字段**（实测响应示例中的结构）：

```
fans_data:
  all_fans_num                 粉丝总数
  gender_distributions         性别分布
  age_distributions            年龄分布          ← 需求点名
  geographical_distributions   地域分布          ← 需求点名
  interest_distributions       兴趣分布
  device_distributions         设备分布
  active_days_distributions    活跃天数
  flow_contributions           流量贡献
```

**同能力族的另外两个接口**（同一「粉丝数据」能力包）：

- 获取用户粉丝来源 —— 仅最近 30 天
- 获取用户粉丝喜好 —— 需 **3000 粉以上**才返回
- 获取用户粉丝热评 —— 需 **3000 粉以上**才返回

**这正是需求要的「粉丝画像、粉丝占比、年龄层分布」，一个字都不差。**

### 门槛（决定它能不能用）

| 条件 | 内容 |
|---|---|
| 开发者资质 | **仅限企业、党政和事业单位**申请 |
| 权限申请 | 控制台 > 应用详情 > 能力管理 > **关系能力 / 关系数据** |
| 授权 | **需要用户授权**——请求参数是 `open_id`，即被查询达人的用户唯一标志 |
| 数据延迟 | 首次授权后**间隔 2 天**才产生全部数据 |
| 数据门槛 | 仅提供**粉丝 > 100** 的用户数据 |
| 审核时长 | 2–3 个工作日 |
| 配额 | 错误码含 `28003017 quota已用完` → **有配额约束** |
| 费用 | 文档未标注按量计费；受权限与 quota 约束。是否收费以申请时平台口径为准 |

### 关键约束：只能查「授权给你的达人」

请求参数是 `open_id`（经 OAuth 换取）。这意味着：

- ✅ **已签约 / 已合作的艺人、达人** → 可让其授权，一次授权长期可取
- ❌ **竞品达人、候选评估阶段的未合作艺人** → 不会授权，拿不到

**这直接决定它解决的是哪一段问题**：

| 业务阶段 | 官方 `fans_data` 能否覆盖 |
|---|---|
| 候选艺人评估（还没合作） | ❌ 不能 |
| 已合作艺人的效果复盘 / 二次投放 | ✅ **能，而且免费** |

### 但它恰好精准命中甲方现在的痛点

需求原文：

> 目前靠人工向艺人索要，效率很低

「人工向艺人索要」＝ 要截图、等回复、格式不统一、无法更新。
`fans_data` 把这件事变成**一次 OAuth 授权 → 接口自动取、持续更新、结构化**。
同一个动作、同一份数据，效率差一个数量级。

**所以对甲方的话术不是「我们要爬抖音」，而是「让合作的艺人点一次授权，粉丝画像就自动进系统了」。**

## 3. 候选评估阶段的通道：星图 / 蒲公英

对**还没合作**的候选艺人，官方 `fans_data` 不适用。这一段要找商业通道。

### 3.1 巨量星图（抖音官方营销平台）

品牌方通过**品牌过审**后，在星图后台可看到达人主页，含：

| 模块 | 字段 |
|---|---|
| 基础画像与粉丝结构 | 粉丝**性别比例 / 年龄分布 / 地域集中度 / 活跃时段**（精确到百分比区间） |
| 内容资产与爆款追踪 | 近 30 天～1 年发布记录、自然流量爆款、历史商单视频，可按播放/点赞率/完播率排序 |
| 商单转化与互动 | 历史合作视频的评论情感分析、商品点击率、搜索指数拉升曲线、预估 GMV 贡献 |
| 报价体系 | 一口价定制 / 视频挂载组件 / 直播带看 / 按效果分成；档期状态与响应时效 |
| 垂类标签与商业评级 | 内容垂直度、粉丝购买力、历史履约质量 → 商业等级 |

筛选维度含粉丝量档位（10w 以下 / 10–100w / 100–300w / 300–500w / 500–1000w / 1000w 以上）、
单视频报价档位、预期播放量、预期 CPM。

**这条路同时补上了另外两个缺口**：
- P1「投流与增量建议」的**数据底座**（有 CPM / 预期播放 / 商单转化）
- P1「艺人（明星）维度」的**报价与商业评级**

### 3.2 小红书蒲公英

官方（`pgy.xiaohongshu.com`）：企业资质 + 开通蒲公英权限后，可看达人**粉丝性别/年龄/地域/兴趣画像**。
**但官方明确不支持批量导出、无历史趋势深度分析**——适合逐个精挑，做不了批量深挖。

第三方 API 服务商把蒲公英封装成 REST（Rnote API / Just One API / 极致了数据等）：

```
GET /api/xiaohongshu-pgy/api/solar/kol/data/userId/fans_profile/v1?token=...&userId=...
→ 粉丝年龄 / 性别 / 地域 / 兴趣 / 设备画像、粉丝增长曲线、活跃 / 互动 / 付费粉丝
```

- 参数只有 `userId` → **可查任意博主**（服务商自己维护蒲公英账号池）
- 按次计费，**仅业务成功才扣费**；错误码含 `601 余额不足` / `602 token 预算超限`
- 服务商自述："普通爬虫接口里拿不到"、"服务端维护账号池并自动调度、限速、轮换"

**这就是需求原文说的「数据公司开放平台／开发者接口采买」的实际形态。**

### 3.3 ⚠️ 明确不要走的路：星图账号租赁

检索结果里出现大量「巨量星图出租 / 品牌过审代办」（淘宝、第三方站点）。
**不要走这条路**：

- 违反平台条款，有**封号**风险（甲方自己的品牌资质可能受影响）
- 数据来源合法性无法证明 → 报告里的 `sourceDeclaration` 就是**假的**
- 与 brandsale 的设计（来源由代码绑定 + fail-closed）**直接冲突**

如果为了省这笔钱走租赁，等于把之前删掉 5 个合成适配器想避免的错误换个形式重犯。

## 4. 分维度可行性：组合方案到底补到哪一步

这是本文的核心交付表。**按需求点名的每个维度分开判断**，不要笼统说「能」或「不能」。

| 需求维度 | ① 检索 | ② 算数指数 | ③ 采集组合 | ④ 官方 fans_data | 综合结论 |
|---|:---:|:---:|:---:|:---:|---|
| 粉丝**总量** | — | — | ✅ 高 | ✅ 高 | 采集层已够 |
| 粉丝**地域**分布 | 品类级 | 关键词级 | ⚠️ **省级代理（有偏）** | ✅ 精确 | **可代理，精确须走 ④/⑤** |
| 粉丝**性别**占比 | 品类级 | 关键词级 | ❌ 无可靠代理 | ✅ 精确 | **须走 ④/⑤** |
| 粉丝**年龄**分布 | 品类级 | 关键词级 | ❌ 无代理 | ✅ 精确 | **须走 ④/⑤** |
| 粉丝**兴趣**标签 | 弱 | ✅ 关键词级 | ⚠️ 内容标签近似 | ✅ 精确 | 可近似，精确走 ④ |
| 粉丝**设备**分布 | — | — | ❌ | ✅ 精确 | 须走 ④ |
| **互动率 / 内容调性** | 弱 | — | ✅ 高 | — | 采集层已够 |
| **报价** | — | — | 现有 M8 报价库 | — | 星图更准 |
| **历史商单转化** | — | — | ❌ | — | 须走 星图 |
| **热榜 / 趋势** | 弱 | ✅ 强（热词） | xhs ✅ / DTK ⚠️未接线 | — | ② + xhs |

**读法**：
- 三个「须走 ④/⑤」的格子，构成了 P0-3 **不可替代的核心**——年龄与性别没有廉价代理
- 地域是唯一能用组合方案做得像样的维度
- ② 巨量算数/抖音指数提供的是**关键词级**画像——配合达人内容标签，
  可以推「这个达人所在内容领域的人群画像」，但**这是内容领域的人群，不是这个达人的粉丝**

**所以必须避免的话术陷阱**：
> ❌「我们用抖音公开数据算出了明星的粉丝画像」
> ✅「我们基于公开的品类人群画像 + 该达人的公开互动数据，给出受众结构的**推断区间**，
>   标注为 L3 未核验；精确画像需艺人授权（官方接口）或走星图（品牌账号）」

后者是诚实的，也是可交付的。前者一旦被甲方交叉验证就会发现偏差。

## 5. 一个一举两得的方案洞察

把两件事放在一起看：

- **P0-3**：需要外部画像数据，但最省钱的那条路（巨量算数网页版）**是人工查询，不是 API**
- **P1-5**：RAG 入库通道缺失——`knowledge.ingest()` 全库只有 `scripts/seed.ts` 一处调用，
  HTTP 层只有只读的 `/kb/retrieve` `/kb/stats`，**没有入库接口**；
  配置里的 `BM_PARSER_URL`（MinerU 解析）**全代码库零引用**，是死配置

**巨量算数（已更名「抖音指数」）网页版有免费的人群画像功能**，按关键词或内容领域可查年龄/性别/地域分布。
甲方运营**人工查一次、截屏或导出**，就是一份可用的画像来源。

于是：**补 P1-5 的入库通道 = 同时给 P0-3 开了一条人工数据入口。**

```
人工在巨量算数查画像 → 录入 KB（新增入库通道）→ 报告通过 RAG 检索引用
→ 来源声明标 L3「巨量算数公开数据 · 人工录入 · 已核验」
```

这条路的优点：
- **零适配器开发**（不需要 DTK，不需要 fans_data 权限）
- **完全合规**（官方公开数据 + 人工核验）
- **同时补掉 P1-5**，让「结合甲方资料更精准」这个卖点真正落地
- 甲方运营本来就在做类似的调研，只是现在没有地方放

**这是投入产出比最高的单个动作。** 建议排在所有数据源接入之前。

## 6. 值得提醒甲方的一件事：需求原文的措辞可以改进

需求写的是：

> 可考虑通过数据公司开放平台／开发者接口采买

按成本与合规排序，正确顺序应该是：

| 顺序 | 路径 | 理由 |
|---|---|---|
| **1** | 抖音开放平台 `fans_data` | **官方、免费**、字段完全对得上；只需企业资质 + 达人点一次授权 |
| **2** | 星图品牌过审 | 官方；可查**未合作**达人；顺带补报价/CPM/商单转化 |
| **3** | 巨量算数网页版 + KB 入库 | 免费；人工成本低；同时补 P1-5 |
| **4** | DTK / xhs 采集 | 补达人内容层与舆情；地域可代理；**不是画像正解** |
| **5** | 第三方 API 采买 | 最后兜底；按次计费；可靠性与合规性由服务商承担 |

**甲方把「采买」放在第一顺位，可能多花不必要的钱**——前三条里有两条是免费的。

## 8. 建议的推进顺序（修订版）

相比 `requirements-coverage-analysis.md` §5 的版本，插入了一条前置项并细化了 P0-3。

| 顺序 | 动作 | 类型 | 说明 |
|---|---|---|---|
| 1 | **补 RAG 入库通道**（P1-5） | 代码 | 一举两得：让甲方能把巨量算数画像、自身资料录进来 |
| 2 | **申请抖音开放平台 `fans_data` 权限** | 商务 | 免费；审核 2–3 天；同时准备达人 OAuth 授权流程 |
| 3 | **补品牌自诊 + 自然语言输入**（P0-1 / P0-2） | 代码 | 纯代码可完成，提升易用性观感 |
| 4 | **接入 DTK 只读子集** | 代码 | 补 P1 达人/内容/舆情 + 地域代理；**接入前先给 `ToolPolicy` 补 `mutating`** |
| 5 | **星图品牌过审 / 蒲公英** | 商务 | 覆盖候选评估阶段；顺带补投流与报价底座 |
| 6 | 第三方 API 采买 | 商务 | 兜底；先小量验证数据质量与稳定性 |
| 7 | xhs | 代码 | 缓接：LICENSE 缺失 + 6.5 个月未更新 + Cookie 依赖 |

**注意顺序 2 与 4 的关系**：`fans_data` 不需要写任何适配器代码就能先启动（申请 + 拉授权），
而 DTK 需要开发。所以**商务动作可以和代码动作并行，不要串行等待**。

## 9. 必须守住的三条红线

1. **不把代理数据洗成实测数据。** 评论 `ip_label` 推出的地域分布，在报告里必须标
   「有偏代理 · L3 未核验」，**不能**和 `fans_data` 的真实画像混在一起呈现。
   这与 P0-2 的 `SourceCatalog` / R6「有数字必须有来源」是同一套约束。
2. **不放松报告的 R6 / R8 校验。** 接入新源后 tier 一律按真实等级标
   （检索/采集类 L3，官方授权类 L1，商业采购类 L4 且需 `legalApproved`）。
   L4 引用仍应被 `validateReportDsl` 拒绝渲染。
3. **不碰账号租赁与灰产数据源。** 来源合法性无法证明，会让整份报告的
   `sourceDeclaration` 变成假的——这是**产品级**风险，不只是合规风险。

## 10. 与两个候选项目的关系（回应原问题）

回到最初的问题：「结合这两个项目的数据再联网搜索，能否支撑 P0-3？」

**答案是：组合后地域维度可做代理级近似，年龄与性别仍必须走官方或商业通道。**

- DTK / xhs 的价值不在画像，在**达人内容层**（账号指标、作品全量、互动、评论、舆情）
- 联网检索的价值在**品类级人群画像**（公开报告）
- 两者组合能得出「这个达人所在内容领域的人群结构 + 这个达人的公开互动健康度」
- 但**推不出**「这个达人的粉丝里有多少是 18–24 岁女性」——这一格只有 ④ / ⑤ 能给

**所以两个项目值得接，但要按它们真实能供的东西接入，不要指望它们解决 P0-3。**
真正解 P0-3 的钥匙在抖音开放平台那一页文档里，而且它免费。
