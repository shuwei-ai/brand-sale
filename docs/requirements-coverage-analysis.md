## 0. 一句话结论

**核心命题成立，可交付形态不成立。**

"输入诉求 → 输出详细策略与预算方案"这条主链路是通的，且已跑过真实模型端到端；
但甲方在文档里逐条点名的 **6 项输出内容 / 3 项数据能力**中，
**有 5 项在代码里完全不存在**（不是没做好，是没有）。
其中「抖音明星粉丝画像」是纯粹的外部数据依赖，**不是写代码能补的**——
这一项决定了产品能不能真的"比人工更准"。

按需求条目折算，当前覆盖度约 **65%（20 条中 11 条满足、4 条部分满足、5 条缺失）**。

## 2. 逐条对照

### 2.1 核心诉求与产品定位（需求 §二、§三）

需求原文：

> 做一个「AI 版策略公司／营销策划公司」：输入一段营销诉求，输出一份详细、可落地的
> 品牌营销策略与预算方案，替代或简化品牌每年在策略公司、策划公司、公关公司上的高额支出。

| 需求 | 现状 | 判定 |
|---|---|---|
| 垂类品牌营销智能体，付费方是品牌方 | 租户模型 `tenantId` + `Brief.brandIds`，鉴权按租户隔离，付费方即品牌方 | 满足 |
| 数据分析 + 策略生成 + 预算测算一体化 | 六阶段流水线：情报（数据分析）→ 人选 → 打法 → 预算（测算）→ 报告，不是单点工具 | 满足 |
| 可结合甲方行业资源与经验数据（RAG） | KB-1/2/3/4 四库 + BM25 检索 + 引用回填，**但入库通道缺失**（见 2.4） | 部分 |
| 不做通用大模型对话工具 | 不是 chat：输入是结构化 Brief，输出是 DSL 驱动的多页报告，中间有工具取数与治理闸门 | 满足 |
| 不做多平台内容矩阵自动生成与发布、图文／视频生成 | 10 个工具里没有任何内容生成 / 发布能力（`validate_brief / resolve_authorization / kb_retrieve / web_search / pricing_query / risk_screen / calendar_plan / scenario_simulate / render_outline / cite_fact`） | 满足 |

**边界守得住**：需求明确排除的两类能力（通用对话、内容生成发布）代码里一条都没有，
没有为了"看起来功能多"而越界扩张。

### 2.2 输入形态 —— 缺口 ①

需求原文：

> 一段自然语言营销诉求，例如：「双 11 想做一场活动，既要曝光和增量，又要销量提升和品牌形象提升」。

现状：`Brief` 是 **8 个结构化字段**（`industry / category / brandIds / budget / objectiveWeights / window / platforms / notes`），
控制台也是填表（行业、类目、品牌 ID、预算、平台多选、三级权重、时间窗口、补充说明）。
`notes` 是唯一自由文本，仅作补充，**不参与任何解析**。

全代码库没有 "自然语言 → Brief" 的解析路径。

判定：**缺失**。
注：AO（任务录入 Agent）已经具备"参数校验 + 澄清问题"的骨架，缺的是"自由文本 → 结构化 Brief"这一段。

### 2.3 输出清单（需求 §四.2，甲方反复强调要「非常详细」）

| # | 需求 | 现状 | 判定 |
|---|---|---|---|
| 1 | **品牌自身诊断分析** | **完全没有。** intake 阶段只做参数合法性校验与授权核验，不产出任何品牌侧诊断；报告 13 页里也没有这一章 | **缺失** |
| 2 | 行业与竞争分析（行业头部是谁、现阶段主要竞品是谁） | 报告「竞品格局对比」表 + 「类目趋势与人群洞察」图；竞品 ≥3 家，每家带内容矩阵 / 声量趋势 / 差异化定位 | 满足 |
| 3 | 营销策略与周期打法（铺料节奏、何时请艺人、何时做直播） | 有阶段化打法（预热/爆发/长尾）+ 按周日历（周序号、起止、平台、内容形态、参与达人、预算份额）。**但"艺人"维度不存在**——库里只有达人（KOL）模型，「直播」仅作为内容形态之一出现，无独立直播排期 | 部分 |
| 4 | 时间节点规划 | 报告「内容日历」timeline 块 + `weeklyCalendar` 周级排期，含 week/from/to/platform/contentType/creatorIds | 满足 |
| 5 | 成本／预算测算（找哪位艺人、需要多少预算、找谁对接） | 人选建议与分层（head/mid/tail + 报价区间）+ 预算分配图 + 渠道×阶段矩阵 + 三档情景模拟。**"找谁对接"不存在**——无商务资源 / 对接方数据模型 | 部分 |
| 6 | **投流与增量建议** | **完全没有。** 没有投流 / 信息流投放的独立分析模块，预算分配里也没有投流口径的拆解 | **缺失** |
| 7 | 最终产物形态：可直接给品牌方看、支撑付费决策的调研报告／策略方案 | HTML 报告 13 页（36KB）：封面 → 来源声明 → 目录 → 核心结论 → 竞品 → 趋势（内联 SVG 图表）→ 人选（象限矩阵）→ 日历 → 预算（图表）→ 渠道×阶段矩阵 → 三档情景 → 风险 → 免责；自动目录带真实页码、打印 A4 分页、来源可溯源、低置信度强制风险提示 | 满足 |

输出侧还额外满足了需求没写、但对"支撑付费决策"很关键的一条：
**不编造数字**——报告 DSL 校验器会拒绝"有数字但既无引用也无来源"的页面，
观测不到的量强制写 `null` 而非估算值。

### 2.4 数据支撑（需求 §四.3）

| # | 需求 | 现状 | 判定 |
|---|---|---|---|
| 1 | 基础层：联网检索（甲方反馈豆包不够准，DeepSeek/ChatGPT 相对可靠） | `volc_web_search`（火山引擎联网搜索 Lite）是**唯一**真实外部源，走完整登记 → 授权 → 闸门流程，`synthetic: false`，L3 分级，白名单开放给全部六个阶段，单任务上限 30 次 | 满足 |
| 2 | 进阶层：结合私域数据与知识库（RAG） | 四库齐备：KB-1 客户授权平台效果库 / KB-2 历史执行与私域知识库 / KB-3 行业公开情报库 / KB-4 方法论与案例模板库；检索用确定性 BM25 + 分面过滤，结果带 `chunkId` 可溯源。**但入库通道缺失**（见下） | 部分 |
| 3 | **关键外部数据：抖音明星粉丝画像、粉丝占比、年龄层分布** | **完全没有。** 5 个平台合成适配器（千川/星图/蒲公英/生意参谋/巨量算数）已被主动删除；L4 第三方数据采购只登记了一个占位源 `l4_example_vendor`，且 `legalApproved: false` → 连授权都没有，**不会出现在报告可声明来源里** | **缺失** |
| 4 | 效率目标：人工 2–3 天，智能体目标约 1 小时 | 真实模型端到端实测 **18 分 17 秒**（intake 11s → intel 129s → creator 171s → playbook 158s → budget 172s → report 455s），总消耗 12.7 万 token | 满足 |

**关于第 2 条的"通道缺失"，这是个容易被忽略但很致命的点**：

- `knowledge.ingest()` 全代码库**只有 `scripts/seed.ts` 一处调用**；
- HTTP 层只有只读的 `POST /kb/retrieve` 与 `GET /kb/stats`，**没有入库接口**；
- 配置里定义了 `BM_PARSER_URL` / `BM_PARSER_FALLBACK`（MinerU 文档解析），
  但 **`config.parser` 在整个代码库零引用**——是一个定义了却没有实现的桩。

结论：甲方的"多年娱乐资源、服务品牌积累的数据"目前**只能由开发改 `seed.ts` 灌进去**。
"结合甲方数据让策略更精准"这句宣传口径，现在落不了地。

### 2.5 前置条件与风险（需求 §六）

| # | 需求 | 现状 | 判定 |
|---|---|---|---|
| 1 | 行业数据是核心门槛（技术方自身没有，需甲方提供或外部采买） | 架构支持（`DataSourceAdapter` 注册表 + 台账登记 + 分级），但除联网检索外**没有任何真实行业数据源**；KB 与报价库种子全是美妆护肤 | **缺失** |
| 2 | 数据隐私（正规获取需走数据公司／开放平台） | 治理闸门是唯一通路，5 项串行检查（scope → source → authz → tenant → semantic），fail-closed；数据源由**代码绑定**而非模型参数决定（防模型自报来源绕过检查）；L4 默认关闭，法务未批即不可用；来源目录只收录"授权生效 + L4 已批"的源 | 满足 |
| 3 | 舆论风险（艺人塌房等不可控，系统只能参考不能承诺结果） | 报告强制包含免责声明页（"不构成投放承诺或收益保证"）、`disclaimer` 字段强制存在、情景一律为区间、低置信度 KPI 页面强制 warn callout、风险登记每条带 owner/signal/mitigation。**但没有公关危机应对模块**（需求提到"公关公司"支出） | 满足（就"不承诺"而言） |
| 4 | 需求必须先定义清楚 | 本文档即是 | 满足 |

### 2.6 待确认问题与下一步（需求 §七、§八）

这两节是**商务 / 范围问题，代码无法回答**，需要甲方拍板：

- 首版聚焦：只做调研报告，还是同时含预算测算与采买建议？（当前代码是"两个都做"，这本身是个超范围假设）
- 甲方可提供哪些私域／文档数据？是否接受外采、费用谁承担？（直接决定 §2.4 第 3 条能不能补）
- 路线：买现成贴牌 vs 自研定制？（决定"RAG 入库通道"要不要做成产品化功能）
- 优先切入的行业与品牌类型？（决定行业数据种子与报价库要铺到什么程度）
- 定价方式：订阅制 / 按份计费 / 项目制？（决定鉴权与配额模型的粒度，目前只有租户级）

## 4. 现有方案的既成优势（不要回退的部分）

1. **可溯源是硬约束，不是提示词愿望**。报告 DSL 的引用校验（R1–R12）会拒绝"无来源数字断言"，
   非法来源降级为 `model_inference/low` 并记入 `degraded`，而不是拒绝出报告——
   避免"把报告不细致换成报告没有"。
2. **三级降级链**（Pi Agent 循环 → 直连结构化输出 → 确定性合成）保证任何一级失败都不中断任务，
   缺失项显式进"排除项"，不静默编造。
3. **治理闸门是唯一通路**，来源由代码绑定，fail-closed。这一条直接对应甲方对数据隐私的顾虑。
4. **效率已达标**：18 分钟 vs 需求给的 1 小时预算，有 3 倍余量去加 P0 内容。
5. **边界守得住**：需求明确排除的两类能力一条都没做。

## 5. 建议的推进顺序

1. **先问甲方**（§2.6 五个问题）——尤其"抖音粉丝画像能不能拿到"，它决定产品是"更快的策略模板"
   还是"更准的策略顾问"，这是付费意愿的真正分水岭。
2. **补 P0-1 / P0-2**（品牌自诊 + 自然语言输入）——纯代码可完成，直接提升"详细"与"易用"的观感。
3. **补 P1-5 RAG 入库通道**——让甲方把数据放进来，才能验证"结合甲方资源更精准"这个卖点。
4. **P0-3 取决于甲方**——拿到数据再接适配器；拿不到就必须在报告里如实标注为公开信息推断。
   已评估两个公开采集类开源项目（DTK / xiaohongshu-cli），结论见
   [`docs/datasource-candidate-evaluation.md`](./datasource-candidate-evaluation.md)：
   二者能补达人 / 内容 / 舆情（P1），**均无法补粉丝画像（P0-3）**——该数据不在平台公开接口内。
5. P1-4 / P1-6 / P2 按甲方确认的首版范围排期。
