# 客户版改造方案（针对《技术方案（实现版）》）

> 内部文档，不对外发送。目标：判断当前文档能不能给客户看、要改什么、改成什么结构。

## 一、结论

**不建议在原文上小修。** 这份文档是一份**研发对账文档**——它的价值在于"我做的和我说的一致"，而这个价值对客户不成立：客户不关心 `validateBlock` 有没有漏 `...sref`，只关心"你能不能交付、多久、多准、出问题谁负责、数据安不安全"。

更麻烦的是它同时踩了三个坑，且**任意一个都可能让客户在尽调阶段卡住**：

| # | 问题 | 严重度 | 客户读到的是 |
|-|-|-|-|
| P0-1 | 非商用许可被写成"红线 + 凭据空缺"（12 处提及） | 🔴 阻断 | "你卖给我的系统里有个组件禁止商用，而且你还没拿到授权" |
| P0-2 | PPTX 缺失被标成 G7 ❌ + 能力矩阵 ❌ + 待决问题（3 处） | 🔴 阻断 | "承诺的交付物没有，还留给我自己发现" |
| P0-3 | 自我批判式表述密集（23 处"实测/真机/缺口/未实现/已移除"） | 🟠 高 | "这套东西还没做完、到处是坑" |

前两个是**口径问题**（需要你先定，见第五节），第三个是**改写问题**（机械可做）。

## 二、三个 P0 的处理

### P0-1 非商用许可：改层级，不改事实

**不能删。** 客户技术尽调一定会看依赖清单和 LICENSE；隐瞒一旦被发现，损失远大于主动披露。但**披露位置和措辞**完全可控——现在是"到处强调 + 明说凭据空缺"，这等于把内部待办贴到客户脸上。

三种处理，按风险从低到高：

| 方案 | 做法 | 优点 | 风险 |
|-|-|-|-|
| A 选配化 + 迁移路径（**推荐**） | 客户版只写："平台公开内容采集为**选配能力**，默认不装配；商用交付时提供两条路径：自建采集通道，或取得上游授权后启用。客户可选择完全不用采集（改用联网检索 + 私域库）" | 事实在、责任边界清、把选择权给客户 | 需商务确认"自建通道"的工作量与报价 |
| B 降级为附录一行 | 只在附录依赖表保留许可证列，正文不提 | 篇幅干净 | 客户技术团队看附录时会追问，反而被动 |
| C 原文照抄 | 保留"红线 + 凭据空缺 + 商用前必须取得书面同意" | 最诚实 | 等于书面告知对方"当前不可商用"，多数客户会直接暂停 |

**推荐 A**，理由：它把事情从"我们的合规缺陷"转成"你的选配项与授权前提"——这是**同一件事实的两种真实叙述**，不是美化。

配套动作：
- 客户版正文只保留一句"采集为选配、默认关闭、可按客户要求不启用"；
- 上游许可与授权状态单独一页放**技术附录**（客户技术团队要看的给足，商务不看的看不到）；
- 内部版保留现在的 4.4 全文，并补一句进度负责人。

### P0-2 PPTX：必须先定商务口径，再动笔

现在文档在三个地方明说"未实现"。这件事**不能靠改词绕过**——客户拿到 HTML 报告时会立刻发现没有 PPT。

需要你先定一个：

1. **本期不出 PPTX**，客户版写成"本期交付 HTML / PDF / Markdown；原生 PPTX 列为增项（含渲染器 + 母版 DSL，独立工作量与报价）"；
2. **本期出 PPTX**，那文档要改成"规划中"，并给出工时与时间点——但要先确认工作量，不能只改文档；
3. **用客户自己的模板**，写成"支持以客户母版导出 PDF/HTML，PPTX 由模板服务承接"。

我倾向 **1**：表述清楚、不留悬念、也不虚承诺。9.1 的 ❌ 和 9.3 的第 3 条相应删除，改到"本期范围 vs 增项"表。

### P0-3 自我批判表述：逐条改写

这不是"说好话"，是**区分"我们的失误"和"产品的边界"**。产品边界要讲清楚（客户靠它设预期），我们的失误属于内部复盘。

| 现文 | 问题 | 客户版改为 |
|-|-|-|
| "这条是商业闭环的关键缺口" | 自我否定，且"关键"二字会被记住 | 删除；结项回灌列入二期范围 |
| "实测某任务证据表 22 条全来自抖音、0 条来自小红书" | 具体事故数字，客户会追问是哪个项目 | "平台数据到达时间不同步时，报告会明确标注该平台本次未取得样本，不会用其他平台数据替代" |
| "修复成本失控 / 白烧 23 分钟 4 万 token" | 内部成本事故 | 删除；改为"确定性问题用确定性函数修复，不消耗模型调用" |
| "凭据空缺 / 未决事项" | 内部待办对外暴露 | 移入内部版 |
| "已从代码中删除（它们只输出伪随机数）" | 自曝曾造假，伤信任 | "当前版本不包含 L1 官方数据源；接入需客户授权后新增适配器" |
| "6 处已修 / 第四层原因 / 两次修正" | 迭代史对客户无意义 | 删除，只留"现已具备"的结论 |

**判断标准**（后续维护也用它）：一句话能不能进客户版，问三件事——
① 客户会不会据此提验收要求？② 它说的是**产品边界**还是**我们的失误**？③ 客户能不能独立验证？
②里的失误一律删；边界一律保留并写清楚。

## 四、必须新增的四节

客户看完架构只会有四个问题，现在文档一个都没正面回答：

| 项 | 指标 |
|-|-|

## 六、执行方式建议

**新建一份"客户版"文档，不覆盖现有文档。** 三个理由：

1. 现有文档是**技术答辩底稿**，客户技术团队提问时要用它（尤其附录里的仓库结构、数据模型、许可证、R 规则）；
2. 覆盖式写入会**丢失白板图**（上次已踩过一次，需手工重插）；
3. 双版本可以并行维护：客户版讲价值与边界，底稿讲实现与细节。

落地为三份，单一来源派生：

```
客户版《技术方案》          ← 对外，商务+业务决策人
技术附录《实现细节》        ← 对外，客户技术团队（现文档 80% 内容）
内部版《实现与风险备忘》    ← 不对外（现文档 + 事故复盘 + 合规待办）
```

维护方式：在 markdown 里用 `<!-- internal:start --> … <!-- internal:end -->` 标记内部段落，导出客户版时脚本剥离。这样以后改一处，两份同步，不会再次出现"客户版说能用、内部版说没做"的分叉。
